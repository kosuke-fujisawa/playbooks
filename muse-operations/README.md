# Muse運用プレイブック ― 他のMuseがそのまま実装できる仕様書

## この文書の使い方（読むMuseへ）

この文書は、人間向けの紹介記事ではない。別の環境で動くMuseが、ユーザーの生活向けに同じ仕組みを実装するための仕様書である。

- 各仕組みは「目的／前提／構成／ジョブ定義／指示文テンプレート／状態管理／失敗モード」の順で定義する。
- 時刻・頻度・件数などの数値は、原運用での実績値である。そのまま使うか、ユーザーの生活リズムに合わせて置き換えること。
- 個人的な事情（家計の目標額、家族の節目など）は一般化してある。実装時にユーザー本人から具体値を聞き、仕組みのパラメータとして設定すること。推測で埋めないこと。
- 実装の順序は、最後の「導入順序」を推奨する。
- 前提プロダクト：Muse（MetaのパーソナルAIエージェント）https://muse.ai 。定期ジョブ、記憶ファイル、連携サービス、ボード（Space）といった、この文書で前提にする機能はMuseのものである。
- 出典がある仕組みには「出典」を付けた。末尾の「出典・参考リンク」にも一覧がある。

## 全体ルール（全仕組みに共通で先に設定する）

### 役割定義
エージェントの役割を一文で定義し、恒常ファイル（IDENTITY相当）に固定する。原運用の定義文：

> 秘書ロボット。生活の側で見回り・実行・記録を担う。判断はユーザーが行い、エージェントは代行しない。

複数AIを使う環境では分担表を作る（例：見回り・定期実行・連携先での下書きと登録＝Muse／文章・コードの作成と独立レビュー＝他のAI）。分担が決まっていると、個別ジョブの指示文が短く済む。

### 承認ゲート
以下は実行前にユーザーへ内容と影響を提示し、承認を得てから実行する。
- 外部への送信・投稿（メール、SNS、メッセージ）
- 購入・予約・課金
- カレンダーへの予定追加
- 外部台帳（ボード、スプレッドシート等）への登録
- データの削除・変更

承認されていない実行結果を「完了」と報告しない。下書き作成までは承認なしで進めてよい。

### 記録の正本分担
- 共通の記憶・経緯：ユーザーが指定するノート基盤（原運用ではNotion）
- タスク：タスク管理サービス（原運用ではTodoist）
- コード：Gitリポジトリ（原運用ではGitHub）
- エージェント自身の記憶：MEMORY相当ファイル。日々の出来事は日次ログ、恒常事実だけを長期記憶へ昇格させる。

### 通知の共通規律
- 通知するのは「ユーザーの判断や行動が変わるもの」だけ。
- 同一の件は14日以内に再通知しない（重大な変化があった場合を除く）。
- 週あたりの通知件数に上限を置く（原運用では監視系で週3件が目安）。
- 候補がゼロの日は、何も送らない。「埋めるための配信」をしない。

## 仕組み1：朝の見回り束

### 目的
朝の開始時に「今日必要なこと」だけを集約して届け、ユーザーが情報源を巡回する手間をなくす。

### 構成（時刻は原運用の実績値）
| 時刻 | ジョブ | 内容 |
|---|---|---|
| 05:12 | 朝刊PDF | 当日の予定・天気・配達予定を新聞風1ページPDFに生成 |
| 07:00 | アバター着替え | その日の天気に合わせてアバターの服装を変更し、天気を一行添える |
| 07:12 | 予定要約 | 当日の本人の予定だけを短く要約 |
| 08:00 | 地域ブリーフ | 居住地域の生活情報（選別基準は下記） |
| 08:12 | メール仕分け | 仕組み2と連動 |

### 実装上の注意
- カレンダーの予定は「作成者」で本人／家族を判別する。家族個人の予定は把握だけに留め、朝の報告に含めない。家族と本人の双方に関わる予定（通院の付き添い準備など）は例外として伝達事項を添える。
- カレンダーの予定と、予約確認メール等で日付・時刻・場所に食い違いがあれば必ず指摘する。大きなイベントの中のプログラムを別予定として入れた時間の重なりは、意図的な内包として競合警告しない。
- アバターの小物ルール例：サングラスは雲の少ない快晴のときだけ付ける。

### 地域ブリーフの指示文テンプレート
```
居住地域について、その日のブリーフを作成する。
載せるのは次の3種のみ：(1) 天気と警報、(2) 生活に直接影響する変更（交通・道路・公共施設・行政の変更や締切）、(3) 大規模イベント（地域の花火大会級、大きな混雑や交通規制を伴うもの）。
小規模な地域行事、神社行事、個別店舗の開店情報は載せない。
該当がなければ「特記事項なし」とだけ書き、件数を埋めない。
```

## 仕組み2：メール仕分けと索引

### 目的
受信トレイの監視をエージェントに寄せ、対応漏れと期限切れを防ぐ。本文を記憶に残さず、検索可能性だけを確保する。

### ジョブ定義
- 朝の仕分け（原運用 08:12）：未読を確認し、対応が必要なものだけを短く要約して通知する。対象の目安：支払い期限が近い請求、返信が必要な連絡、予約・手続きの変更。
- 昼の無言巡回（原運用 13:12）：通知しない。読んだメールを索引へ追記するだけ。

### 索引の形式（1行1件、本文は転記しない）
```
日時 | 送信者 | 件名 | 話題1行 | 種別 | message_id
```

### 状態管理
- 状態ファイルに「最後に処理した位置（ウォーターマーク）」を保持する。
- 取得に失敗した回はウォーターマークを進めず、失敗理由を状態ファイルに残す。次回は同じ位置から再試行する。

### 配信停止の処理（付随運用）
- ワンクリック配信停止が使える送信元はバッチで処理する。結果の報告表現は「endpoint accepted（受け付けられた）」までとし、「停止が確認できた」とは書かない。実際にその後も届くかを後日の巡回で検証する。
- ワンクリック非対応の送信元は、サイト側の設定変更が必要なものとして別リストに分け、ユーザーに渡す作業指示書（対象サイト、禁止事項、確認手順）を作る。

## 仕組み3：公式連携のないメッセージングサービスの橋渡し

### 目的
公式APIや連携機能を持たないメッセージングサービス（原運用ではLINE）の見落としを防ぐ。ただしチャット本文をクラウド側へそのまま渡さない。

### 構成
- ローカル側（ユーザーのPC上の別エージェント）が、デスクトップ統合アプリ（原運用ではBeeper）経由で対象サービスを読み取り専用に読む。
- 差分だけを、非公開の共有フォルダへ定期的に書き出す（原運用では1日2回、08:00と20:00）。
- Muse側は書き出しを、朝の仕分け（08:12）と夜の確認（20:12）に合わせて読み、対応が必要なものがあるときだけ通知する。

### ルール
- Muse側から書き出しファイルの編集・削除をしない。対象サービスへの送信はしない（読み取り専用）。
- 認証コード、URL、その他本文中の機微な要素は通知に転記しない。
- 読み取り位置（ウォーターマーク）をMuse側のファイルで管理し、二重通知を防ぐ。
- 書き出しの仕様（対象、形式、頻度）は共有フォルダ内の仕様書を正本とし、口頭合意で運用しない。

### 失敗モード
- 書き出しが止まると無言で見落としが再発する。書き出しファイルの最終更新時刻を健康診断（仕組み11）の確認項目に入れること。

### 出典
- Beeper Desktop API（ローカルAPIとMCPサーバの公式ドキュメント）: https://developers.beeper.com/desktop-api/
- Beeper Desktop MCP の設定手順: https://developers.beeper.com/desktop-api/mcp/
- ローカル側の読み取りは、このMCPサーバ経由で行う。MCPエンドポイントはローカルホストで待ち受けるため、読み取りはユーザーのPC上で完結する。

## 仕組み4：習慣の声かけと記録

### 目的
睡眠・運動・読書などの習慣を、意志ではなく「声かけ→実施→一言報告→記録→次回調整」のループで回す。

### 睡眠
- 就寝計画をパラメータとして設定する（原運用：23:00にスマホを充電器へ置く、23:30に布団に入る、06:30起床）。
- 声かけジョブは計画の約45分前（原運用 22:12）。文面には、その日読んでいる本を「開く」一言を添える（読書の維持枠と連動）。
- 遅い帰宅の日用に代替ルールを1つ決めておく（原運用：「帰宅後すぐにスマホを充電器へ」）。
- 朝のチェックインで前夜分を記録する。健康データ（スマホの睡眠記録）が取れる場合は自動判定し、取れない場合は本人に就寝時刻を聞く。データがないことを端末設定の不備と決めつけない。
- 記録スキーマ：日付／就寝時刻／スマホを置いた時刻／判定（守れた・滑った）／起床時刻／本人の感想メモ。
- 失敗モード：端末側に睡眠データ自体が記録されていない場合、自動判定は成立しない。その場合は申告制に切り替え、自動化の前提が崩れていることを健康診断に載せる。

### 運動
- アナウンスは1日2回（原運用：朝06:40と夜22:15）。実施はどちらか一方でよい、と指示文と文面の両方に明記する。
- メニューは曜日固定にする。負荷の大きい日（原運用：週2回の筋力メニュー）と軽い日（5分程度）を分ける。
- 実施後は本人が一言報告する。記録には実施内容ときつさ（RPE）を残し、次回の負荷調整ルールに使う：前回RPEが低く回数をこなせていれば目標回数を+1、前回RPEが高いか回数をこなせていなければ据え置きか軽減。痛みの報告があれば負荷を上げない。
- 回数の申告がない項目は、メニューの既定値を「仮記録」と明記して記録し、実績と混同しない。

### 読書
- 平日は「本を開く」だけの維持枠（1ページでも可）、週末に1回1〜2時間の集中枠、という二層にする。並行読みはせず1冊に集中する。
- 購入と読書状況は外部の読書記録サービスを正本とし、エージェント側は台帳で追跡する。未読があれば月1回だけそっと確認する。
- 週次チェックイン（原運用：日曜夜）で、スクリーンタイムと一緒に「開いた日数・週末枠の実施・読んでいる本」を聞く。

### 声かけ文面の共通ルール
責める言い方をしない。「体調が悪い日は休んでよい」「どちらか一方でよい」など、滑っても戻れる余白を文面に入れる。

## 仕組み5：支出の用途確認フローと家計の検算

### 目的A：精算が必要な支出の用途を、忘れる前に確定する
対象は、利用通知がメールで届く決済手段（原運用：家族カード）で、支出ごとに「共有の支出か、他者への精算が必要か」の判定が要るもの。

#### フロー
1. 利用通知メールを短い間隔で巡回する（原運用：3時間おき）。
2. 店舗名が載る詳細通知を待たず、利用日と金額だけの速報の段階で本人に用途を聞く。
3. 確認前に、カレンダー（その日の予定）と金額が一致する注文メールと照合し、用途の推測が付けば「推測」と明示して提示する。照合しても不明なものは推測で埋めずに聞く。
4. 本人が思い出せないものは「用途未確定リスト」に残し、詳細通知で店舗名が判明した時点で本人に知らせる。
5. 精算が必要と確定したものは、タイトル形式を固定したカードを精算台帳へ登録する。形式テンプレート：`金額円（M/D 用途 貸付分）`。登録前にタイトル案を提示し、許可を得てから登録する（承認ゲート対象）。
6. 共有の支出と分かったものは台帳に登録しない。対象外の店舗カテゴリ（日用品の共有購入など）は、ユーザーと合意して除外リスト化する。

### 目的B：家計の診断を、検算してから出す
- 家計サービスと連携し、残高・明細を読み取り専用で直接確認する。
- 月の診断は「収入−生活支出」ではなく、月の純増減を基礎にし、銀行口座の残高変化と突き合わせて検算してから出す。内訳は少なくとも「生活支出／他者への精算・返済／貯蓄・投資への移動／未分類の送金」に分解し、自分の口座間移動を支出に数えない。
- 家族内送金など、一般的な分類と実態が違う項目は、ユーザーの実態に沿った分類ルールを恒常ルールとして記録する（例：家計サービス上で「借金返済」と分類される家族への送金が、実在の精算であるケース）。誤分類と決めつけて扱わない。
- 貯蓄目標（金額と期限をパラメータ化）に対し、必要ペース＝残額÷残月数を計算し、週次で進捗を確認する。
- 支出の週次チェックで、カテゴリ別の日常支出を集計する。特定カテゴリ（原運用：交際費）に月額上限をパラメータ設定し、超えたらその月に一度だけ、累計額と主な内訳を添えて知らせる。
- サブスクリプションは月次で棚卸しし、年額課金のものを月額の見直し候補に混ぜない。
- 現金の扱い：完全捕捉を目指さない。銀行明細のATM出金合計を現金支出の総額（上限）として報告し、内訳は本人が申告した大きな支出だけを記録する。過去の出金の用途を後から聞かない。

### ダッシュボードの表示ルール
先頭は診断のみ（直近の確定月が黒字か赤字か、赤字なら原因と対策、注意点は最大3件）。サマリーは文章ではなくグラフィカルに表示し、明細とグラフは根拠として後ろに置く。

## 仕組み6：記事・論文のピックアップ（選別基準を育てる）

### 目的
ユーザーの思考を前に進める材料だけを選んで届ける。汎用的な実務ノウハウ集めではない。

### 構成
- 毎晩（原運用 20:12）、フィード群を巡回する。原運用のフィード種別：技術ブログ全体フィード、タグ別フィード、論文フィード（ソフトウェア工学、HCI）、ブックマーク人気。
- フィードURLの実例：Zenn全体 https://zenn.dev/feed ／ arXiv cs.SE https://rss.arxiv.org/rss/cs.SE ／ arXiv cs.HC https://rss.arxiv.org/rss/cs.HC 。タグ別フィードやブックマーク人気は、各サービスのRSS仕様に従って構成する。
- 既読管理：状態ファイル（JSON）に取得した全リンクを保存し、新着だけを候補にする。配信したものも落としたものも既読に加える（二度出し防止）。
- 論文はPDFが取得できるものを優先し、リンクを添える。

### 選別基準の置き方（重要）
- 選別基準はジョブの指示文そのものに書く。基準は固定ではなく、ユーザーの評価で書き換え続ける前提で運用する。
- 配信後にユーザーが評価（「薄い」「テクニックに寄っている」「問題提起が浅い」等）をしたら、その言葉を除外条件・優先条件の文に翻訳して、指示文へ追記する。感想のまま保存しない。
- 原運用で収束した基準の例：主軸は学術論文（対象領域はユーザーの関心に合わせて設定）。ブログ等の実践レポートは「問題提起の深いもの」だけ。分業や運用の具体は合格条件ではなく前提条件。数値改善を前面に出すもの、ツールの検証、ハウツー、手法の適用記録は除外。迷うものは落とす。ゼロ件の日があってよい（量より的中率）。

### 失敗モード
- 基準を緩めると件数は増えるが的中率が下がり、ユーザーの評価でさらに締める往復になる。最初から狭く始め、ユーザーが「拾ってほしい」と言ったカテゴリだけを足す。

## 仕組み7：変化の監視

### 目的
「逃すと困る変化」（申込期限、発売、開催可否、重要な活動）を、ユーザーが追い続けなくて済むようにする。

### 監視の定義テンプレート（1テーマ1定義）
```
テーマ / 監視対象の情報源 / 通知条件（何が起きたら知らせるか）/ 頻度 / 見直し日
```

### 共通ルール
- 通知条件は「ユーザーの判断や行動が変わるものだけ」に限定する。
- 同一の件は14日以内に再通知しない。週の通知上限を置く（全体ルール参照）。
- 各監視に試行期間と見直し日を先に設定し、見直し日に基準ごと評価して、残す／直す／捨てるを決める。ユーザーの確認なしに「試験中」から「稼働中」へ格上げしない。

### 原運用の監視例（カテゴリのみ）
- 関心テーマの新知見（週次〜月次、テーマ別）
- よく見るアーティスト・配信者の重要な活動（週1回。発売・公演発表・チケット発売・休止/復帰のみ。本人の参加可否に条件がある場合は、その条件とセットで判定する）
- 年に一度級の地域イベントの開催アナウンス（月1回）
- 参加予定イベントの参加者ブリーフィング（イベント前に、参加者一覧とユーザーとの関係を可能な範囲で調べる）
- 特定の実践者の発信ウォッチ（週1回。本人が実際にやった具体例だけを最大3件、なければ送らない）

## 仕組み8：ライフイベントの見守りと期限管理

### 目的
期限・手続き・調べものが継続的に発生するライフイベント（家族の節目、大きな契約など）を、週次の定型で見守り、抜けを防ぐ。

### 構成
- 週1回、カレンダーの関連予定を確認し、その時期に一般的に推奨される準備・申し込み等のアクションを提案する。
- 健康・医療に関わる内容は、出典つきの一般情報のみを出す。個別の診断・助言はしない。
- 本人が同席できない予定（家族の通院など）については、準備と確認事項を「本人から家族へ伝える前提」の形でまとめる。
- 期限のある手続き（予約、入金、申し込み開始日時）は、期限レジストリ（対象／期限／状態）で管理し、近づいたら知らせる。
- 大きな調べもの（制度、手続き、施設選び）は、会話で流さず初回調査の資料ファイルとして残す。未確認事項は未確認と明記する。
- 契約もの（定期配送など）は、特典の条件、変更・キャンセルの締切、無料期間の終了日と自動更新のタイミングを管理対象にし、判断が必要な日の前にリマインドする。

## 仕組み9：AI間タスクブリッジと夜間テスト

### 目的
ユーザーのローカル環境でしか実行できない作業（ローカルリポジトリの操作、ローカルアプリの実行）を、クラウド側のMuseから依頼し、結果を回収する。あわせて、夜間に自動で回帰確認を行う。

### フォルダ構成（共有ストレージ上）
```
（ルート）
├─ 00-仕様.md        … 運用仕様の正本
├─ タスク/           … 依頼側が置くタスクファイル
├─ 結果/             … 実行側が書き戻す結果ファイル
└─ 素材/             … 受け渡し用ファイル
```

### 運用ルール
- 状態の正本は「結果ファイルの有無」。実行側の進捗の自己申告では判断しない。
- タスクファイルは書き換えない。再試行は新しい連番で作る。
- タスクのヘッダに「定期実行：可」と明記したものだけ、実行側の定期チェック（原運用：毎時）が自動実行する。無印のタスクは通知のみ。
- 別のタスクの「置き換え」と明記されたタスクがある場合、置き換え元のタスクは実行禁止。
- 実行側の前提条件（対象ストレージの接続、作業ツリーがクリーン、他エージェントが同じリポジトリで作業中でないこと）を満たさなければ実行せず、理由を結果ファイルに書く。前提で止まった場合も結果ファイルを残す（不在＝未実行か停止か判別できなくなるため）。

### 夜間テストのパターン
1. 夜のジョブ（原運用 22:12）が、その夜の確認観点を設計する。観点は対象領域のローテーションで決め、前回失敗があればその回帰確認を優先する。
2. ブリッジ経由でローカル側へ実行タスクを置く。実行内容は既存テストのフル実行＋観点に沿った確認。コード修正とテストコードの新規作成は禁止する。
3. 実行側は結果ファイルを書き戻し、あわせてレポートのみのブランチを切ってプッシュする。
4. Muse側は結果を処理し、PRを作成して別のAIへレビューを依頼する（コメントでメンション）。
5. 本人への通知は、失敗がある場合のみ。成功時は状態ファイルへの記録のみ。

### 判断の残し方
仕様か不具合かの判定、チケット化、マージはユーザーの側に残す。自動化するのは「実行、記録、一次分類（既知／新規／環境要因）」まで。

### 出典
- この「設計と実行とレビューの分業」パターンの参考：vivisuke「Museを使ってQA工程を『全身を赤く塗ってもいいほど』爆速化（当社比）した話」Qiita, 2026-11-11。 https://qiita.com/vivisuke2025/items/a78d245c4040e6e60c00 。Museに調査・検証・修正を任せつつ、変更権限と最終判断は人間に残す分業の実践記録で、夜間テストの分業設計はこれを下敷きにしている。

### 失敗モード
- ブリッジが止まると、タスクだけが溜まり続ける。結果フォルダの最終更新と未処理タスク数を健康診断（仕組み11）で確認する。

## 仕組み10：普段触れない分野の紹介枠

### 目的
情報収集が関心範囲だけに閉じないよう、最適化の対象外の「遊び枠」を仕組みとして残す。

### ルール（原運用）
- 週3回（月・水・金の夕方）、ユーザーが普段触れない分野からテーマを1つ紹介する。本人の専門・仕事の分野には寄せない。驚きと多様さを優先し、役立つ必要はない。
- 紹介後に感想や理解度の確認を求めない。反応がないことを嫌悪と解釈しない。
- 紹介したテーマと分野はログに残し、重複させない。

## 仕組み11：AI自身の健康診断

### 目的
仕組みが増えると、止まっている連携や未確認のままの処理にユーザーが気づけなくなる。定期的にエージェント自身を棚卸しする。

### 棚卸し項目
- 定期ジョブ：総数、有効／無効、期限切れの一回限りジョブ、重複した追跡項目
- 記憶：長期記憶ファイルの量、ファイル総数、日次ログの日数
- カスタムスキル／プロジェクト用フォルダ／ボード類の数と棚卸し候補
- 連携サービス：接続状態。表示上の「接続済み」ではなく、実際にデータを1件取得できるかで確認する
- 止まっている仕組み：ブリッジの結果フォルダの最終更新、計測系の実績件数（例：睡眠の自動記録が0件のまま）、結果未確認のバッチ処理

### 出力形式
- ボード（Space等）の先頭は診断のみにし、「止まっているものだけ」に絞って出す。全項目を並べない。
- 棚卸し結果は記録ファイルにも残す。

### 処理の進め方
- 処理してよいもの（期限切れジョブの削除、未確認バッチの再実行など）は、ユーザーの指示を受けてその場で処理する。
- エージェント側で処理できないもの（ユーザーの端末設定、ローカル側の調査が必要なもの）は、その旨を明記して分離する。進んでいるふりをしない。

### 出典
- この仕組みの着想は「Muse健康診断ボード」の提案投稿（X、そらとひかり @noctiluce_sora、2026-11-16。中村としや @tsyn18 による続報投稿も同趣旨）。自分のMuseの記憶・仕組み・連携の状態をボードに可視化するという提案で、原運用ではそこに「止まっているものだけを先頭に出す」「実データ取得で接続を確認する」を足して実装した。投稿の個別URLは未確認のため、著者と日付で示す。

## 導入順序（推奨）

1. 全体ルール（役割定義、承認ゲート、正本分担、通知規律）を先に設定する。
2. 仕組み1（朝の見回り）と仕組み2（メール）を入れる。効果が早く出て、運用の型が決まる。
3. 仕組み4（習慣）、仕組み5（家計）など、ユーザーの困りごとが明確なものから足す。
4. 仕組み6・7（選別と監視）は基準が育つまで時間がかかる前提で、狭く始める。
5. 仕組み3・9（橋渡し系）は、ローカル側の協力体制ができてから。
6. 仕組み11（健康診断）は、仕組みが10件を超えたあたりで入れる。

最後に：この文書の各仕組みは「ユーザーのどの困りごとから来たか」とセットで意味を持つ。実装時は形の複製ではなく、ユーザーの困りごとへの置き換えから始めること。
